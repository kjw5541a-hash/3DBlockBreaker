# 3DBlockBreaker 설계안

작성일: 2026-09-03

## 1. 개요

아르카노이드(벽돌깨기)를 기반으로 하되, 두 가지를 바꾼다.

**보는 방식.** 2D 탑뷰가 아니라 기울어진 판을 원근으로 본다. 블럭은 종류에 따라 높이가 달라 기울기 덕에 입체로 읽힌다.

**치는 방식.** 공은 일정 속도로 움직이지 않는다. 판 아래로 당기는 중력을 받으며, 패들에 그냥 맞으면 에너지를 잃어 도달 높이가 줄어든다. 탁구처럼 앞으로 밀어야 가속하고, 패들을 기울여 치면 방향이 바뀐다. 좌우 이동은 손가락을 그대로 따라가지만, 앞으로 밀기와 기울이기에는 속도 제한이 있다.

아이템은 원작 7종을 그대로 쓴다.

## 2. 기술 스택

Godot 4.7.2 / GDScript. 웹 export 후 GitHub Pages 배포, 폰 세로 화면 터치가 1순위 플랫폼. 데스크톱 마우스는 개발·테스트 용도로만 지원한다.

`~/games/blockbox` 와 동일한 파이프라인이며, 홈 dotfiles 저장소와는 별개의 독립 저장소다.

### 물리는 직접 구현한다

Godot 내장 3D 물리(`RigidBody3D`)를 쓰지 않는다. 벽돌깨기는 rigidbody 의 약점 위에 정확히 올라앉는다. 빠른 공이 얇은 블럭을 통과하는 터널링, 슬립, 미세 스핀으로 매 판 달라지는 반사각, 공이 벽과 거의 평행해져 돌아오지 않는 상태가 모두 발생한다.

더 결정적으로, 이 게임의 핵심 규칙 셋(속도 하한 clamp, 패들 속도 전달, 최소 반사각 강제)은 전부 엔진 솔버를 거스르는 개입이다. 매 프레임 엔진이 계산한 값을 덮어쓰게 되고, 디버깅이 남의 솔버 안에서 벌어진다.

대신 공의 위치와 속도를 직접 적분하고, 충돌은 원-AABB 수학으로 푼다. 블럭이 격자라 브로드페이즈는 배열 인덱싱이면 충분하다. 움직이는 물체는 공 하나뿐이고 충돌 상대는 축정렬 상자뿐이라 코드량이 작다. 튜닝 상수가 전부 한 파일에 노출되고, 물리 함수가 순수 함수라 헤드리스 테스트가 가능하다. Godot 은 그리기와 입력만 담당한다.

## 3. 공간과 좌표계

### 월드 배치

플레이 판을 X축 기준 25° 기울여 월드에 놓는다. 카메라는 판 앞쪽 위에 고정한다. 판이 실제로 기울어져 있으므로 블럭 높이가 원근에 따라 드러나고, 아래쪽 블럭일수록 옆면이 더 보인다.

기울기 각은 순수 시각 파라미터다. 중력 크기를 `g·sin(θ)` 로 묶지 않고 독립 상수로 둔다 — 묶으면 튜닝 노브 두 개가 하나로 붙어 조정이 불편해진다.

### 물리 좌표

물리는 판 위의 2D 로컬 좌표 `Vector2(u, v)` 에서만 계산한다.

- `u` — 좌우. 범위 `[-5, +5]`, 판 폭 10 유닛
- `v` — 플레이어 쪽이 0, 블럭 쪽이 위. 범위 `[0, 16]`
- 중력은 `-v` 방향 상수

렌더링 계층이 `(u, v)` 를 판 로컬 `(x, 0, -v)` 로 옮긴다. 기울기 각을 바꿔도 물리 코드는 바뀌지 않는다.

### 구역

| 구간 | 내용 |
|---|---|
| `v < 0` | 데드존. 공 소멸, 목숨 1 차감 |
| `v ∈ [0.4, 3.0]` | 패들 밴드. 패들 중심의 이동 범위 |
| `v ∈ [3.0, 9.0]` | 자유 공간. 아이템 낙하 구간 |
| `v ∈ [9.0, 15.0]` | 블럭 격자. 10열 × 6줄, 셀 1.0 × 1.0 유닛 |
| `v = 16` | 상단 벽 |
| `u = ±5` | 좌우 벽 |

판 비율 10:16 은 폰 세로 화면에 맞춘 값이다.

### 사거리 계약

속도 하한을 "패들 밴드 아래끝 `v=0.4` 에서 출발해 최하단 블럭 줄 `v=9.0` 에 겨우 닿는 속도"로 정의한다.

```
V_MIN = sqrt(2 · GRAVITY · 8.6)
```

이 한 식이 게임 규칙의 중심이다. 살살 받으면 아래 두 줄만 건드리고, 위 네 줄에 닿으려면 실제로 밀어야 한다. 하한이 곧 기본 사거리이므로 스윙에 의미가 생긴다.

## 4. 물리 규칙

### 적분

고정 타임스텝 120Hz, 렌더링과 분리한다(`_physics_process`). 한 스텝의 이동거리가 공 반지름을 넘으면 그 스텝을 서브스텝으로 쪼갠다 — 고속 공의 터널링 방지.

공은 위치와 속도만 갖는 점질량 + 반지름이다. 회전과 스핀은 없다.

### 감쇠는 패들에서만 나온다

벽과 블럭의 반발계수는 1.0 으로 에너지를 잃지 않는다. 패들만 0.80 이다.

에너지를 빼는 곳이 한 군데뿐이라 "왜 공이 느려졌나"의 답이 언제나 "그냥 받았으니까"가 된다. 벽에서도 잃게 만들면 인과가 흐려지고 튜닝 노브가 셋으로 늘어난다.

### 패들 반사

```
법선 n = 패들 기울기 각도 + 접촉점 오프셋 기여(패들 중심에서 벗어난 만큼, 최대 ±20°)
v_out = reflect(v_in, n) · PADDLE_RESTITUTION + 패들속도 · PADDLE_SPEED_TRANSFER
v_out = clamp_speed(v_out, V_MIN, V_MAX)
v_out = enforce_min_angle(v_out, MIN_ANGLE)
```

이 네 줄이 게임의 조작 요구사항 전부를 만든다.

- 가만히 받기 → 속도 0.80배 → 몇 번 왕복하며 도달 높이가 눈에 띄게 줄다가 `V_MIN` 에서 멈춘다
- 앞으로 밀기 → 패들 속도가 실려 가속, 상단까지 도달
- 기울여 치기 → 법선이 회전해 반사 방향이 바뀐다
- 접촉점 오프셋 → 패들을 안 움직이고도 좌우 조준이 된다. 패들 각도가 이동 속도에서 유도되므로, 이 항이 없으면 가만히 받을 때 수직 반사만 나온다
- `enforce_min_angle` → 공이 수평에 가까워져 좌우 벽만 튕기며 내려오지 않는 교착을 막는다

### 튜닝 상수

| 상수 | 초기값 | 의미 |
|---|---|---|
| `GRAVITY` | 12.0 | 판 아래방향 가속도 |
| `BALL_RADIUS` | 0.25 | |
| `PADDLE_RESTITUTION` | 0.80 | 유일한 에너지 손실원 |
| `PADDLE_SPEED_TRANSFER` | 0.60 | 스윙이 공에 실리는 비율 |
| `V_MIN` | 14.4 | `sqrt(2·G·8.6)`. 최하단 블럭 줄에 겨우 닿는 속도 |
| `V_MAX` | 34.0 | 조작 가능 상한 |
| `MIN_ANGLE` | 15° | 수평 교착 방지 |
| `CONTACT_ANGLE_MAX` | 20° | 접촉점 조준 폭 |

### 체감 확인

초기값 기준으로, 최대 속도 30 으로 친 공을 이후 계속 가만히 받으면 30 → 24 → 19.2 → 15.4 → 14.4(하한)로 떨어진다. 네 번 왕복에 걸쳐 도달 높이가 눈에 보이게 줄고, 그 뒤로는 최하단 줄만 긁는다. 다시 위를 치려면 밀어야 한다.

### 충돌 판정

원-AABB. 공 위치를 셀 좌표로 바꾼 뒤 주변 3×3 셀만 검사한다. 별도의 공간 분할 자료구조는 없다.

블럭 모서리에 맞으면 면 법선이 아니라 중심-접촉점 벡터를 법선으로 잡는다. 두 블럭 사이 틈에 낀 공이 발작하는 것을 막는다.

## 5. 패들 조작

### 터치를 판 좌표로

판이 25° 기울어 있으므로 화면 좌표를 그대로 쓸 수 없다. 터치점에서 카메라 광선을 쏴 판 평면과 교차시켜 `(u, v)` 를 얻는다. 손가락 밑에 패들이 정확히 오는 감각이 여기서 결정되므로 근사하지 않는다.

### 패들은 순간이동하지 않는다

목표 위치(손가락)를 향해 축별 최대속도로 추종한다.

| 축 | 최대속도 | 이유 |
|---|---|---|
| `u` (좌우) | 40 u/s | 사실상 손가락에 붙어 다닌다 |
| `v` (앞뒤) | 22 u/s | 밀기에 제한을 준다 |

순간이동을 허용하면 패들 속도가 무한대로 튀어 공에 비정상적인 힘이 실리고, 텔레포트가 공을 그대로 통과한다. 추종 최대속도가 곧 스윙 세기의 상한이다. 별도의 쿨다운, 게이지, 스윙 애니메이션 상태기계는 만들지 않는다.

### 패들 각도는 좌우 속도에서 유도

```
tilt = clamp(paddle_vel.u × K, ±30°)
```

오른쪽으로 휘두르면 패들이 오른쪽으로 기울어 법선이 회전하고 공이 오른쪽으로 날아간다. 실제 탁구 라켓과 같은 인과다. 최대 기울기 30° 는 좌우속도 25 에서 도달한다.

각도는 프레임 간 lerp 로 살짝 눌러 지터를 없애되, 계수를 높게 잡아 반응 지연을 만들지 않는다.

### 패들 속도는 3프레임 이동평균

터치 샘플링에는 지터가 있어 한 프레임 델타를 그대로 쓰면 정지 상태에서도 속도가 튄다. 이 값이 공에 실리고 각도까지 결정하므로 노이즈를 그대로 먹이면 안 된다.

### 패들도 스윕 판정

빠른 패들이 느린 공을 지나쳐버릴 수 있다. 공의 서브스텝과 같은 이유로, 패들은 이전 위치에서 현재 위치를 잇는 캡슐로 충돌을 본다.

### 발사

공을 잃거나 스테이지를 시작하면 공은 패들에 붙는다. 위로 스윕하면 그 스윙 속도가 초기 속도가 된다. 탭만 하면 `V_MIN` 으로 수직 발사한다. 첫 입력부터 스윙 문법을 가르치므로 별도 튜토리얼이 필요 없다.

### 규격

패들 반폭 1.0 유닛(판 폭의 20%), 두께 0.3.

## 6. 블럭

10열 × 6줄 격자. 종류는 원작과 같이 셋이다.

| 종류 | 내구 | 높이 | 외형 |
|---|---|---|---|
| 일반 | 1 | 0.4 | 색상별, 점수 차등 |
| 단단 | 3 | 0.6 | 은색, 맞을 때마다 어두워짐 |
| 불괴 | ∞ | 0.8 | 금색 |

높이는 순수 시각 값이다. 물리 충돌은 여전히 `(u, v)` 평면의 AABB 이고, 높이는 메시 두께만 정한다. 기울어진 판에서 높이 차가 원근으로 드러나 입체감을 만들면서 물리는 2D 로 남는다. 단단한 블럭이 물리적으로도 두꺼워 보이는 것은 부수 효과다.

스테이지 레이아웃은 텍스트 그리드 파일로 정의한다(`.` 빈칸, `1-8` 색상, `S` 단단, `G` 불괴). 판 하나를 추가하는 데 코드 수정이 필요해서는 안 된다.

## 7. 아이템

원작 7종을 이 게임의 물리에 맞춰 해석한다.

| 아이템 | 효과 | 처리 |
|---|---|---|
| **E** Enlarge | 패들 반폭 1.0 → 1.5 | 접촉점 조준 폭도 함께 넓어진다 |
| **C** Catch | 공이 패들에 붙는다 | 붙은 뒤 스윙하면 그 속도로 발사. 기존 발사 로직 재사용 |
| **L** Laser | 패들에서 위로 발사, 블럭 1히트 | 물리와 무관한 별개 투사체 |
| **S** Slow | 물리 타임스케일 0.7 | 속도를 직접 곱하면 `V_MIN` clamp 와 싸운다. 시간을 늦추면 물리 규칙을 건드리지 않고 체감만 느려진다 |
| **D** Disruption | 공 3개로 분열 | 공을 배열로 돌린다. 각 공이 독립적으로 clamp 와 감쇠를 받는다 |
| **B** Break | 워프 게이트, 통과 시 즉시 다음 판 | |
| **P** Player | 목숨 +1 | |

### 드랍과 획득

블럭 파괴 시 12% 확률로 아이템이 떨어진다. 중력이 아니라 등속 4 u/s 로 내려온다 — 공이 이미 가속하는 물체라 아이템까지 가속하면 잡을 수 있는지를 순간 판단할 수 없다.

패들 AABB 에 닿으면 획득한다. 한 번에 하나만 활성이며 새 것을 먹으면 이전 것이 해제된다. 원작 규칙이고, 조합 폭발을 막는다.

> 드랍 확률과 생성 규칙은 추후 별도 논의 대상이다.

## 8. 진행

목숨 3. 불괴가 아닌 블럭이 전멸하면 클리어한다. 점수는 블럭 종류별 점수와 클리어 보너스의 합이며 최고점은 로컬에 저장한다.

1단계에서는 판 하나만 만든다. 스테이지 순서, 개수, 연출은 손맛 확정 후 2단계에서 정한다.

## 9. 렌더링과 화면

### 카메라

판 앞쪽 위에 고정, 원근투영 FOV 40°. 직교로 하면 입체감이 통째로 사라지고, FOV 를 넓히면 가장자리 블럭이 왜곡돼 조준이 거짓말이 된다. 물리는 판 좌표계에서 도므로 원근 왜곡과 무관하다.

판 10:16 전체가 폰 세로 화면 세이프 에어리어 안에 들어오도록 카메라 거리를 맞춘다.

### 공 속도를 화면에 노출한다

플레이어가 알아야 할 유일한 숨은 상태는 "지금 공이 센가 약한가"다. 공 트레일의 길이와 색을 속도에 비례시킨다. `V_MIN` 근처면 짧고 흐리게, `V_MAX` 근처면 길고 밝게. 숫자 게이지는 쓰지 않는다.

감쇠가 진행되는 것이 눈에 보여야 밀어야겠다는 판단이 나온다.

### 조명과 그림자

방향광 하나. 공과 패들만 그림자를 드리우고 블럭은 받기만 한다(웹 export 와 폰 성능). 공은 판에서 살짝 띄워 그려 그림자가 존재감을 만들게 한다. 판에 딱 붙이면 그림자가 공에 가려 아무 정보도 주지 않는다.

### 타격 피드백

블럭 파괴 시 파편과 아주 짧은 카메라 셰이크, 패들 강타 시 셰이크. 둘 다 미세하게 준다. 기울어진 판에서 흔들림이 크면 조준 기준선이 흔들려 조작감을 해친다.

### HUD

점수, 목숨, 활성 아이템을 판 위아래 여백에 얇게 배치한다. 판 옆에 세로 패널을 두지 않는다 — blockbox 에서 우측 세로 패널이 폰에서 플레이 영역을 가린 문제가 이미 있었다.

시작 화면에 브랜치와 커밋을 표시하는 blockbox 관행을 그대로 가져온다. 폰에서 미리 볼 때 어느 빌드인지 구분하기 위해서다.

### 블럭 렌더링

최대 60개이므로 개별 `MeshInstance3D` 로 충분하다. MultiMesh 배칭은 하지 않는다. 60개는 부담이 아니고, 배칭하면 개별 파괴 애니메이션이 즉시 번거로워진다.

## 10. 테스트

물리가 순수 함수이므로 헤드리스 Godot 에서 assert 로 검증한다. blockbox 의 `run_tests.sh` 패턴을 재사용한다. 단일 파일 실행은 반드시 `perl -e 'alarm 40; exec @ARGV' -- ...` 같은 시간 제한으로 감싼다. 실패한 assert 가 헤드리스 Godot 을 무한 정지시키기 때문이다.

실제로 회귀 위험이 있는 지점만 하나씩 검사한다.

| 검사 | 깨졌을 때의 증상 |
|---|---|
| 감쇠 수열 30 → 24 → 19.2 → 15.4 → 14.4 에서 멈춤 | 무한 감속 또는 clamp 미작동 |
| `V_MIN` 이 `v=9.0` 에 닿고 `v=9.5` 에 못 닿음 | 사거리 계약 붕괴 |
| `V_MAX` 공을 블럭에 던져 관통하지 않음 | 터널링 |
| 거의 수평으로 발사 후 `MIN_ANGLE` 이 복구 | 좌우 벽 교착 |
| 두 블럭 틈으로 공 던지기 | 모서리 낌 |
| 빠른 패들 vs 느린 공 | 패들 스윕 실패로 공 놓침 |

고친 뒤에는 변이 테스트로 검사가 실제로 잡는지 확인한다.

## 11. 구현 단계

### 1단계 — 물리 검증

**포함:** 판 1개, 일반 블럭만, 공 1개, 패들 조작 전부, 물리 전부, 속도 트레일, 목숨 3과 리셋, 튜닝 상수 파일, 웹 export 와 GitHub Pages 배포.

**제외:** 아이템 7종 전부, 단단 블럭과 불괴 블럭, 스테이지 진행, 점수와 최고점, 파편과 셰이크, 사운드.

손맛이 나오지 않으면 아이템 7종은 전부 헛일이 된다. 물리 튜닝값은 실제로 손가락으로 쳐보기 전에는 정할 수 없다.

**1단계의 산출물은 코드가 아니라 다음 다섯 개의 답이다.**

1. `PADDLE_RESTITUTION` 0.80 과 `PADDLE_SPEED_TRANSFER` 0.60 — 감쇠와 가속의 비율. 손맛의 중심.
2. 앞뒤 최대속도 22 — 밀기 제한이 답답한지 헐거운지.
3. 최대 기울기 30° 와 접촉점 20° — 조준 폭이 충분한지.
4. `GRAVITY` 12 와 `V_MIN` 14.4 — 왕복 리듬이 지루한지 정신없는지.
5. 판 10×16 과 블럭 10열 × 6줄 — 비율이 맞는지.

### 2단계 — 내용

1단계의 다섯 답이 나온 뒤에 아이템 7종, 블럭 3종, 스테이지 진행, 점수, 연출, 사운드를 얹는다.
